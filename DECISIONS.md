# DECISIONS

Журнал решений. Формат записи: метка времени (`date -Iseconds`), что решили, почему, какие альтернативы отброшены.

## 2026-10-04T13:57:37+06:00: Структура репозитория и менеджер пакетов

**Решение:** монорепо на npm workspaces (`backend`, `frontend`), без общего пакета типов на старте.

**Почему:** npm идёт вместе с Node, и проверяющему не нужно ставить ничего лишнего. Workspaces позволяют запускать скрипты из корня. Общие типы пока не нужны: API маленький, пакет добавлю, когда появится дублирование.

**Отброшено:**
- pnpm: быстрее, но это лишняя зависимость на машине проверяющего.
- Отдельные репозитории: в задании требуется монорепо.
- Turborepo/Nx: для двух пакетов это избыточно.

## 2026-10-04T13:57:37+06:00: Миграции

**Решение:** `drizzle-kit generate` + применение миграций при старте backend, а не `drizzle-kit push`.

**Почему:** SQL-миграции лежат в git, изменения схемы видны в истории, и они воспроизводимы в docker.

**Отброшено:** `push`, потому что он не оставляет истории и опасен на живых данных.

## 2026-10-04T14:26:21+06:00: Инфраструктура в docker compose

**Решение:** `postgres:16-alpine` и `axllent/mailpit` с именованными volume (`pgdata`, `mailpit`). У Postgres есть healthcheck через `pg_isready`. Порты и учётные данные берутся из env со значениями по умолчанию, шаблон лежит в `.env.example`.

**Почему:** именованный volume нужен для требования «после перезапуска ничего не теряется». Проверено вручную: таблица пережила `docker compose down` + `up`. Healthcheck позволит backend стартовать только после готовности БД (`depends_on: condition: service_healthy`). Mailpit хранит письма в SQLite на volume, поэтому после перезапуска письма тоже не пропадают.

**Отброшено:**
- bind-mount `./data`: ломается на правах доступа и засоряет репозиторий.
- Postgres 17: в 16 нет ничего, что нам мешало бы, а 16 лучше проверен с pg-boss и Drizzle.
- Отдельная тестовая БД в compose: пока не нужна, тесты будут создавать свою схему или базу. Решу на шаге с тестами.

## 2026-10-04T14:28:33+06:00: Устройство backend

**Решение:** `buildApp(deps)` отделён от `server.ts`, зависимости (пока только `pingDb`) передаются явно. Конфиг из env проверяется через zod, у всех полей есть значения по умолчанию для локального запуска. Dev-режим запускается через `tsx watch --env-file-if-exists`, без dotenv.

**Почему:** тесты используют `app.inject()` без поднятия порта, и сбой БД легко подменить (тест на 503). `/health` честно проверяет БД (`select 1`), потому что docker healthcheck backend будет на это опираться. Встроенный `--env-file` в Node убирает лишнюю зависимость.

**Отброшено:**
- Fastify-плагины с декораторами (`app.decorate('db')`) на старте: явные зависимости проще тестировать. Могу вернуться к этому, когда появятся сервисы.
- Миграции при старте добавлю вместе с первой таблицей. С пустой схемой папки миграций нет, и `migrate()` упадёт.
- pg-boss подключу на шаге с фоновыми задачами: в каркасе он ни к чему.

**Заметка:** npm 11 не запустил postinstall у esbuild (новая защита install-scripts). tsx и vitest работают, потому что бинарник ставится через optionalDependencies.

## 2026-10-04T14:30:30+06:00: Устройство frontend

**Решение:** шаблон Vite `react-ts`, Tailwind v4 через `@tailwindcss/vite` (без `tailwind.config` и PostCSS). Фронт обращается к API по относительному `/api/*`, Vite proxy срезает префикс и проксирует на `API_TARGET` (по умолчанию `http://localhost:3000`). У Playwright есть `webServer`: если `E2E_BASE_URL` не задан, он сам поднимает backend и vite.

**Почему:** один origin для браузера, поэтому не нужен CORS, и SSE потом пойдёт через тот же proxy. В docker поменяется только `API_TARGET`. Smoke-тест проверяет всю цепочку: браузер → vite → backend → postgres.

**Отброшено:**
- CORS и абсолютный URL API во фронте: лишняя настройка и разные URL в dev и docker.
- Tailwind v3 с PostCSS: в v4 меньше конфигурации.
- oxlint из шаблона: удалён, линтер не входит в заданный стек. Если понадобится, добавлю позже одним шагом.

**Заметка:** `npm audit` показывает 4 moderate. Все идут из старого esbuild внутри `drizzle-kit` (уязвимость dev-сервера esbuild, который мы не запускаем). Это dev-зависимость, в рантайм не попадает. `audit fix --force` откатил бы drizzle-kit, поэтому не применяю.

## 2026-10-04T14:32:56+06:00: Запуск всего стека в docker compose

**Решение:** production-подобные образы. Backend собирается через `tsc` и запускается как `node dist/server.js` (только prod-зависимости). Frontend собирается статикой и отдаётся nginx, nginx проксирует `/api/` на backend с `proxy_buffering off` и долгим `proxy_read_timeout` под SSE. Контекст сборки — корень монорепо, чтобы использовать общий `package-lock.json`. Фронт снаружи на :8080, порт 5173 оставлен для локального vite. Healthcheck backend проверяет `/health`, frontend стартует после healthy backend.

**Почему:** проверяющий запускает одну команду и получает то же поведение, что в проде: один origin, SSE через прокси. Настройки nginx под SSE заложены заранее, чтобы потом не ловить «live-счётчик не обновляется» из-за буферизации.

**Отброшено:**
- Vite dev-сервер внутри docker с bind-mount: медленный file watching на macOS, и это не прод-поведение.
- Отдельный `package-lock` на каждый пакет: противоречит npm workspaces.

**Грабли:** в alpine `localhost` резолвится в `::1`, а Fastify слушает `0.0.0.0` (IPv4), поэтому healthcheck падал с connection refused. Теперь в healthcheck стоит `127.0.0.1`.

## 2026-10-04T14:42:58+06:00: Схема событий и регистраций

**Решение:** две таблицы. В `events` есть `CHECK capacity > 0`. В `registrations` статус задаётся enum `confirmed | waitlisted | cancelled` (одна строка проходит путь от листа ожидания до места и отказа). Порядок в листе ожидания задаёт `seq bigserial`. Код билета (`ticket_code`) и токен управления (`manage_token`) — разные поля. Страховки на уровне БД:
- частичный уникальный индекс `(event_id, email) WHERE status <> 'cancelled'`: не больше одной активной регистрации на email;
- `CHECK`: код билета есть ровно у confirmed. У cancelled код остаётся для истории.

Миграции генерирует `drizzle-kit generate`, backend применяет их при старте (`migrate()`), папка `drizzle/` копируется в образ. Тесты работают на отдельной базе `events_test` в том же Postgres: `globalSetup` создаёт её и накатывает миграции, каждый тест начинает с `TRUNCATE`, файлы тестов идут последовательно.

**Почему:**
- Одна строка со статусом вместо отдельных таблиц для мест и листа ожидания: переход из листа на место становится одним `UPDATE`, и строка не теряется между таблицами.
- `seq` вместо `created_at`: в одной транзакции и при одновременных вставках метки времени могут совпасть, а `seq` монотонный.
- Отдельный `manage_token`: код билета короткий, его вводят руками на входе. Если бы по нему же можно было отменить регистрацию, любой, кто видел код, мог бы снять человека с события.
- Повторная регистрация после отказа разрешена (новая строка в конце очереди), поэтому индекс частичный.

**Отброшено:**
- Таблицы `tickets` и `waitlist` отдельно от регистраций: перенос между ними требует двух операций, и легче получить рассинхрон.
- `citext` для email: нормализую в коде (`trim` + `lowercase`), одно место вместо расширения Postgres.
- Тесты в транзакциях с откатом: тесты на гонки отправляют параллельные запросы через пул соединений, внутри одной откатываемой транзакции гонки не будет.
- Схема на каждый тестовый файл: пока файлов мало, последовательного запуска достаточно.

**Грабли:** `globalSetup` в vitest не видит `test.env`. Переменные выставляются в `process.env` прямо в `vitest.config.ts`.

## 2026-10-04T14:45:29+06:00: Регистрация и гонка за места

**Решение:** регистрация идёт в транзакции, которая начинается с `SELECT … FROM events WHERE id = $1 FOR UPDATE`. Внутри транзакции: найти активную регистрацию на этот email (если есть, вернуть её), посчитать confirmed, вставить confirmed с кодом билета или waitlisted. Если частичный уникальный индекс всё же сработал, ловлю ошибку и отдаю существующую запись. При коллизии кода билета транзакция повторяется (до 3 раз).

Ответы API:
- новая регистрация → `201` с `ticketCode` и `manageToken`;
- повтор → `200 { alreadyRegistered: true, status }` **без** кода и токена;
- событие уже началось → `409`.

**Почему:**
- Блокировка строки события по очереди пропускает все операции над одним событием, разные события друг другу не мешают. Счётчик мест пересчитывается внутри блокировки, поэтому лишнее место выдать нельзя.
- Повтор не раскрывает токен: иначе любой, кто знает чужой email, получил бы ссылку на отказ и код билета. Билет человек получает в ответе на первую регистрацию и по почте (письма — шаг 3).
- Код билета: 8 символов из алфавита без похожих символов (0/O, 1/I/L), это около 8·10¹¹ вариантов. Токен управления: 24 случайных байта (base64url).

**Проверка, что тесты на гонку не формальные:** временно убрал `FOR UPDATE` и запустил тесты 5 раз. Каждый раз падали 4 теста: на гонку и на счётчики. С блокировкой 5 прогонов из 5 зелёные.

**Отброшено:**
- `SERIALIZABLE` + повтор при ошибке 40001: тоже корректно, но цикл повторов нужен на каждой операции, и сбои под нагрузкой сложнее отлаживать.
- `pg_advisory_xact_lock(hash(event_id))`: работает, но блокировка строки нагляднее и не требует хешировать uuid в bigint.
- Условный `INSERT … SELECT … WHERE (select count) < capacity` без блокировки: при READ COMMITTED две транзакции видят одинаковый count, а это та самая гонка.

## 2026-10-04T14:48:56+06:00: Отказ и переход из листа ожидания

**Решение:** `POST /registrations/:manageToken/cancel`. Транзакция: блокировка события → **перечитывание регистрации под блокировкой** → `cancelled` → если она была confirmed, `fillSeatsFromWaitlist`. Эта функция считает свободные места (`capacity − confirmed`) и выдаёт их первым по `seq` с новым кодом билета и `promoted_at`. Повторный отказ возвращает `200 { alreadyCancelled: true }` и ничего не меняет. После начала события отказ даёт `409`. Сервис возвращает список продвинутых: на него в шаге 3 повесим письма, поставленные в очередь в той же транзакции.

**Почему:**
- `fillSeatsFromWaitlist` заполняет все свободные места, а не одно. Тогда функция сама себя исправляет: её можно вызвать и при увеличении лимита (пригодится позже), и двойной вызов не выдаст лишнего.
- Перечитывание под блокировкой обязательно. Без него отказ из листа ожидания, пока он ждал блокировку, мог «не заметить», что человека уже продвинули: место снимается, а следующий в очереди его не получает.
- Новичок не обгоняет очередь: освободившееся место уходит листу ожидания в той же транзакции, поэтому свободного места при непустой очереди не бывает. Это тоже покрыто тестом.

**Проверка тестов поломками:**
- убрал `FOR UPDATE` → падают 2 параллельных теста на отказы;
- убрал перечитывание под блокировкой → сначала тесты остались **зелёными**: через параллельные HTTP-запросы окно гонки ловилось ненадёжно. Добавил детерминированный тест: он вручную держит блокировку события, меняет состояние, пока отказ ждёт (ожидание видно по `pg_stat_activity`), и только потом отпускает. Теперь эта поломка ловится 3 из 3 раз.

**Отброшено:**
- Продвигать ровно одного человека на каждый отказ: ломается, если места освобождаются иначе (изменение лимита) или если вызов повторится.
- Отказ по email: любой, кто знает адрес, мог бы снять человека с события.

**Ещё:** у тестов появился свой `tsconfig.test.json`, раньше `tsc` проверял только `src`, а vitest типы не проверяет.

## 2026-10-04T19:38:03+06:00: Письма: pg-boss + журнал отправок

**Решение:** письма ставятся в pg-boss **внутри той же транзакции**, что и изменение данных (`boss.send(..., { db })` на том же соединении через свой `withTx`). Задача несёт только `kind`, `registrationId` и `dedupKey`. Воркер под `pg_advisory_xact_lock(dedupKey)`: проверяет `email_log` → проверяет, что письмо ещё актуально (не отказался, «лист ожидания» не уходит после продвижения) → отправляет через SMTP → пишет в `email_log`. Если SMTP упал, транзакция откатывается, и pg-boss повторит задачу.

**Почему:** сервер может упасть в любой момент, а письмо не должно ни потеряться, ни уйти без места. Повторы отсекает журнал, потому что очередь гарантирует только «хотя бы один раз». Содержимое письма собирается при отправке из актуальных данных.

**Честное ограничение:** если SMTP уже принял письмо, а процесс упал до коммита записи в журнал, после перезапуска письмо уйдёт повторно. С SMTP «ровно один раз» не гарантировать, окно здесь — миллисекунды.

**Отброшено:** отправка письма сразу после коммита без очереди (падение между коммитом и отправкой = потерянное письмо); `singletonKey` pg-boss вместо журнала (защищает только от дублей в очереди, не от повторного выполнения задачи).

**Тесты:** почта подменяется в памяти, задачи разбираются вручную. Интеграционный тест на перезапуск: письмо поставлено, pg-boss остановлен без воркера, новый экземпляр отправляет его в настоящий Mailpit ровно один раз. Один прогон набора из трёх упал, повторить не удалось (0 из 18). Вероятная причина — хелпер ожидания блокировок считал и advisory-блокировки pg-boss; исключил их.
